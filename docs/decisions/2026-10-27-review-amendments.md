# 评审后的补充：Bun 前提、U 内置资源闭包、Desktop 抽包推迟、四类不是上限

日期：2026-10-27。状态：已拍板。补充并部分取代同日的 [create-alwith-npm-only](2026-10-27-create-alwith-npm-only.md) 与 [create-alwith-inside-u](2026-10-27-create-alwith-inside-u.md) 中的论证；结论不变。

## npm 是分发渠道，Bun 是执行环境

两者不是同一个选择。发到 npm 不自动保证只装了 Node 的用户能跑 `npm create alwith`。删除"生成的项目反正要 `bun install`，所以 Bun 必有"的循环论证，准确理由是：本轮统一采用 Bun 工具链；U 自带固定版本的 Bun；CLI 用户明确需要安装兼容版本。对外本轮只承诺经过测试的 `bun create alwith`，以后若宣传 `npm create alwith`，再验证并提供 Bun 检测或引导。

## U 内置的是经验证的资源闭包

"内置 npm 包就是多拷一个目录"不准确。U 内置的是经验证、可由自带 Bun 执行的完整脚手架资源及其运行依赖，并测试安装后路径与离线启动。是否单文件打包由实现决定。

## 本轮不要求 Desktop 同步抽包

旧文"工具链检测安装抽一个包、项目创建与运行托管抽一个包，Desktop 与 U 都装"推迟。普通用户关键路径是零本地工具链，Launchpad 安装抽包不该挡住首个结果。先复用实际可复用的实现；U 的托管契约验证后，再让第二个消费者接入。"实现不能有两份"的原则不变。

## 四类是本轮默认交付地图，不是上限

黑盒、包、registry block、模板描述的是可见性、交付方式和生成时机，不是互斥的架构层，shadcn 也证明不了"四层上限"。改为：本轮采用这四类交付方式，不新增独立的交付机制；发现现有分类无法容纳的实际需求时，先说明所有权、生命周期和升级路径，再评审是否调整。平台契约允许自写页面、替换组件、经协议采用其他 UI 技术；本轮不做其他框架模板。
