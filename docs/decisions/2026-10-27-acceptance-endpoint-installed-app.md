# 一小时的终点是安装自己的产物，不是 U 内预览

日期：2026-10-27。状态：已拍板（Claude 与 Codex 评审一致，用户要求"一小时做出"）。

## 问题

普通用户线的验收终点写成"在 U 里能运行"是否足够。

## 决定

普通用户与开发者使用同一终点：安装自己的产物，退出 U 后独立打开，完成登录、聊天、审批、看历史，并完成一个小而真实的业务定制。一小时是从下载开始到上述全部完成的墙钟时间，包含首次认证、定制、云端构建排队、下载与安装；失败重试不暂停计时。

零工具链交付因此进入本轮关键路径。本轮若只能交付 U 内预览，只能称"阶段验收"，不得宣称一小时目标达成。

## 为什么

在 U 中预览一个前端，证明不了用户获得了可安装、可独立登录和使用的应用。把终点降到预览，当前范围全部完成也兑现不了开头的承诺。

## 推论

- 主路线是带依赖缓存的云端构建。预编译通用壳只是待验证优化：现有 Tauri 工程把前端目录嵌入二进制（`frontendDist` 经 codegen 进入 `EmbeddedAssets`），"换资源即可"需要另做资源装载设计，必须固定能力集合、资源装载方式、品牌处理和签名路径四项再评。
- 第一遍"发现"先在 nyssance 账号下用 GitHub Actions 验证最小云端交付：从公开发行物装依赖、构建、签名、下载到干净机器安装、退出 U 后独立启动、五件事走通，并分别记录冷缓存、热缓存、排队、构建、签名、下载、安装耗时。GitHub Actions 是验证环境，不是面向用户的产品服务；第三遍普通用户验收必须由 U 完成提交、进度展示和取产物，不能让普通用户配置仓库、Secrets 或工作流。
- 构建缓存可以作为生产条件，但必须是服务正常提供的缓存，不能靠维护者为单次验收预热。兑现不了一小时就保留阶段成果并报告瓶颈，不改终点。
