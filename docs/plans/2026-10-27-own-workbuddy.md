# 用公开发行物创建自己的桌面 Harness

立项：2026-10-27。当前口径整理：2026-11-01。状态：实施与验收中；本次文档整理不代表功能或最终验收完成。

## 目标与终点

用户通过 create-alwith，在一小时内创建自己的桌面 Harness，在自己的电脑上编译并独立运行。WorkBonny 是实际验收样本；生成器和共享默认能力才是可复用的产出。

开发者可从 `bun create alwith` 开始；普通用户从 U 的创建入口填写应用名、目录与 identifier，创建后在项目聊天中继续定制。两条入口使用同一个生成器，不维护两套创建逻辑。

终点遵循[本地编译运行决策](../decisions/2026-10-29-local-build-endpoint.md)：提供可执行的工具链前提、生成、构建与运行命令，生成项目不依赖维护者工作区或私有源码。U 托管预览、云端构建服务、证书购买或托管、签名公证、下载安装不是 create 流程或本轮验收前提。已有云端 CI 只作为构建证据。

一小时是待实测的目标，不是已兑现的结论。创建之外仍须验证聊天、审批、历史和真实定制；选择 ALwith 账号模式时还须验证平台登录与该模式的默认能力。

执行约束见 [AGENTS.md](../../AGENTS.md)，拍板理由见[决策索引](../decisions/index.md)。2026-10-27 的[评审记录](../reviews/2026-10-27-codex-review.md)保留为历史，不覆盖后续范围修正。

## 默认产品必须完整

第一版 WorkBonny 原样消费共享 U 标准，先完成默认模板，再由用户明确选择产品定制。模板只负责品牌、模块组合和必要接线，不自行设计主题、间距、圆角、包装面板或缩水页面。

- 聊天、项目选择、项目与活跃会话、历史、审批、原生窗口操作必须实际可用。
- 默认菜单的折叠、悬停展开、hover、active、走马灯，以及账号菜单与多语言入口，使用共享实现。
- 设置使用标准分类、设置项和独立窗口；-1 屏接入已启用能力对应的扩展、插件、Skills 等入口。
- 缺失的默认值、样式或行为回所属上游补齐，再由模板原样接入；不在 WorkBonny 或模板中维护替代实现。
- 用户可整体替换页面。不要用大量样式参数替代明确的页面所有权，也不要让定制反向污染默认模板。

细项与验收动作见[默认模板完整性审计](2026-10-30-template-default-audit.md)。界面可打开、类型检查或构建通过，都不能替代入口与行为验收。

## 创建时选择账号能力

遵循[账号选择决策](../decisions/2026-10-29-optional-account.md)：

| 选择 | 默认装配 |
| --- | --- |
| 集成 ALwith 账号 | 标准登录、账号设置及宠物相关能力 |
| 不集成 ALwith 账号 | 不装配该账号体系和宠物；保留不依赖账号的聊天、项目、活跃会话、设置、扩展／插件／Skills 等能力 |

不集成账号不等于功能缩水的“纯聊天”。模型供应商认证与 ALwith 平台登录分开，文档分别说明入口、账号前提与费用；不能隐含使用维护者登录态。可选能力按用户选择和启用模块装配。

## 所有权与交付边界

| 所有者 | 职责 | 消费与升级 |
| --- | --- | --- |
| `@nyssance/atlas` | 通用布局、页面轨道、几何、手势和分页机制；标准分页不包含 -1 与尾部页面 | 消费公共配置与接口，不含 ALwith 业务导航或品牌 |
| `@alwith/module-desktop-shell` | 桌面壳默认呈现、窗口与菜单机制、Atlas 接线、通用底栏及状态呈现 | 应用传入业务数据和事件；共享默认值在包内维护 |
| `@alwith/module-*` | 聊天、认证、存储、扩展等能力及可组合组件 | 好东西先进包，U 和其他应用再消费 |
| `@nyssance/codex-acp-v2` | ACP 能力、Codex 扩展、项目与会话投影 | 新建与导入使用同一适配器契约；Codex 元数据归适配器 |
| `@alwith/api` | Runtime 公共封装 | 不保留 `_meta` 字段、协议投影或兼容转导出 |
| `@alwith` registry block | 默认登录、聊天、设置、侧栏等页面组合 | 用户可整体替换；来源和版本可追溯 |
| create-alwith 模板 | 品牌配置、模块组合、工程配置和必要接线 | 记录生成器版本、文件所有权与基线 |

不新增独立交付机制；确有容不下的需求，先说明所有权、生命周期和升级路径。平台允许替换页面，本轮不增加其他 UI 框架模板。

应用统一消费公共能力，并不要求产品布局相同：U、Desktop、WorkBonny、GitCub 接入适用的共享壳能力；Desktop 可替换底栏与圆点，缩略图是独立能力；GitCub 底部留白 16、不显示底栏与分页。TV 保留原版画板布局，不新增左侧菜单。差异通过已有公共配置或整体替换表达，不改共享默认实现。

## 生成器与工程约定

create-alwith 位于 ALwith-ai 的独立公开仓，按 AGPL v3 交付，TS 跑在 Bun 上，只发 npm。本轮继续暂停 create-alwith 的新版本发布；可从本地候选验证，无需发布后才能调试。

- 模板随发行物提供；交互和非交互入口共享实现。U 与 Agent 使用结构化进度、错误和结果，不解析终端文案猜测成功。
- 缺少必要输入、非空目录冲突或执行失败时明确报错，保留用户文件；无绝对必要禁止自动重试、退避或专门的重试流程。默认无遥测。
- 项目名、应用显示名、identifier 和目录由用户确定。目录输入表达清楚最终生成路径，不重复设置相互冲突的位置。
- 品牌唯一来源为 `alwith.app.json`；生成的配置和元数据可含品牌，手写源文件不得重复定义。用两个品牌验证生成与构建，无默认品牌残留。
- `@alwith/*` 使用 `^`，实际版本由 bun.lock 锁定。正式依赖不得使用 link、file、workspace 或维护者绝对路径。
- 允许 Cargo path 指向公开 npm 包内的 Rust 源码，解析结果必须留在公开发行物内。
- 记录生成器、Bun、Rust、Runtime、适配器、原生依赖、registry 摘要及 Bun/Cargo 锁文件；manifest 与锁文件保持一致，执行冻结安装和锁定构建。
- 同一版本和相同输入应确定性生成。离线承诺只到模板展开；依赖获取仍需网络或已提供的缓存。
- 页面与样式使用共享来源；模板不维护从 U 复制后独立演进的默认实现。registry 页面记录来源与基线，用户修改后通过差异预览决定升级。
- 本轮不提供 migrate、三方合并、画布型或其他框架 preset。

## 调试与运行安全

生成项目提供真实可执行的本地开发命令与工具链前提，不承诺用户无需安装工具链。Hasgard 优先用于运行中应用的快照、交互和日志验证；不可用时记录原因并使用合适的替代工具。

Codex 由 Runtime 托管，不自行 spawn，不另建会话库。测试默认用 mock；所有启动 Runtime 的脚本，包括临时探针，使用 `startTestRuntime` 和临时 CODEX_HOME。仅显式授权的 live 测试可通过 authFrom 复制认证，并保证释放资源。

暂存或安装时逐字节保留厂商签名的 Codex 与 code-mode-host，不做 ad-hoc 或 --deep 重签。运行签名检查；发行签名沿用已有 CI 配置。

## 持续验证闭环

1. 固定一批本地候选包，在隔离环境中验证；候选路径不进入正式 manifest 或锁文件。
2. 用 WorkBonny 品牌配置重新生成，两种账号模式、两个品牌均覆盖。检查默认页面、入口、交互与共享标准一致。
3. 发现差异记录[缺口台账](../gaps.md)，回所属模块或 registry 修复，再重新生成；不在模板和 WorkBonny 补替代实现。
4. 检查类型、前端与原生构建、依赖独立性、原生签名；用 Hasgard 验证实际入口和行为。默认测试不创建真实模型会话。
5. 核对生成器拥有文件的确定性；用户拥有文件按接口、行为和明确的定制记录验收，不强求产品源码完全相同。
6. 对受影响消费者完成兼容验证后，统一发布已完成的包集合，再更新正式依赖与锁文件，复核公开发行物生成结果。create-alwith 的暂停发布要求单独遵守。

CI 应真实生成和构建，U 内置生成器也须验证打包后的路径与依赖闭包。不能以临时 tarball 构建成功代替公开发行物独立性验收。

## 验收与测量

以下是完成标准，具体状态与证据由缺口台账和专项审计记录；文档清理不自动关闭任何缺口。

| 条目 | 完成标准 |
| --- | --- |
| 独立性 | 无维护者源码和私有发行物凭据，从公开发行物生成、冻结安装、构建、独立运行 |
| 默认完整性 | 两种账号模式按选择完整装配；项目、活跃会话、菜单、设置、扩展／插件／Skills 等实际可操作 |
| 无本地绕过 | 临时 patches 和应归上游的复制实现已清除；无局部样式覆盖冒充共享修复 |
| 可复现 | 同版本同输入生成一致；双品牌无残留；配置、锁文件与发行闭包一致 |
| 真实功能 | 聊天、审批、历史可用；账号模式登录及相关能力可用；未授权的真实测试明确记为未验证 |
| 业务定制 | 用户描述一个真实需求，完成一次修改，并验证重启后的结果和状态 |
| 兼容性 | 受影响消费者验证共享接口与各自产品布局；当前先验 macOS，Windows 实机暂缓 |
| 时间 | 外部首次使用者按预先固定任务独立完成，记录完成率及完整耗时，不以维护者熟练操作代替 |

计时前固定机器、系统、网络、缓存、工具链、账号与订阅前提及任务。开发者从执行 create 命令起算，普通用户从开始获取 U 起算；记录工具链准备、首次认证、生成、依赖安装、定制、编译、启动与功能验证。缺失工具链的准备耗时必须披露，不事后排除失败或调整计时口径。没有建设的云端交付环节不进入必测流程。

## 历史阶段证据：2026-10-29 账号选择的本地候选验证

- create-alwith 的 CLI 和 U 的创建表单传递同一个 `auth` 选择；账号模式带宠物，不集成账号的模式删除相关代码、直接依赖和原生权限。
- 使用实际打包的 auth / desktop-shell 候选归档，在两个隔离的新项目中完成离线安装、前端类型检查和构建、原生资源暂存、Rust 编译及独立性检查。正式 package.json 和 bun.lock 未混入本地候选路径。
- 生成器 10 项测试、共享模块 164 项测试、宠物原生 20 项测试通过；U 的 86 项脚本测试、1,437 项应用测试、255 项 Rust 测试、类型检查、knip、生产构建和 clippy 通过。同事升级 ACP SDK 后的测试数据已补齐 command 类型字段。
- Hasgard 验证了候选应用的登录界面；未使用真实账号执行完整宠物交互，未启动真实模型测试会话。这部分不记为端到端验收通过。
- 新增本地候选验收脚本和 U 的显式 `CREATE_ALWITH_PATH` 开发入口。截至该次验证，本批功能未发布；此处仅保存当日证据，不代表当前发行状态。
